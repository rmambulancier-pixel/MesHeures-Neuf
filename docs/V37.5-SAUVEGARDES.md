# MesHeures V37.5.0 : sauvegardes, import et restauration

Base : V37.4.1 (arbre `86804dcf`), branche `v37.5.0-tests-dates`. Fichier principal : `app/src/main/assets/web/scripts/app-backup.js`.
Calculs, règles d'heures, paie, `app-core.js`, modules Planning (`app-v372-*`) et Comparaison (`app-v373-*`) : non modifiés.

## 1. Convention de version

Trois notions distinctes :

| Champ | Sens | Utilisé pour décider ? |
|---|---|---|
| `format` | identifiant du fichier : `MesHeures Backup` | oui |
| `formatVersion` | version de la **structure** du fichier (entier) | oui |
| `version` | version de l'application qui a écrit le fichier (`meta application-version`) | **non**, information seulement |

`formatVersion` :

| Valeur | Structure | Première version |
|---|---|---|
| 1 | `data` (DB) seule | V36 et V37.0.0 |
| 2 | + `romiMaster` (relevés ROMI1) | V37.0-0 (fondations) |
| 3 | + `plannings` (plannings prévisionnels) | V37.2.0 |

Les fichiers écrits avant V37.5.0 n'ont pas de `formatVersion` : leur structure est déduite des blocs présents, comme avant.
Un fichier dont `formatVersion` dépasse 3 vient d'une version plus récente et il est refusé avec un message.

Pourquoi ne pas se fier à `version` : les fichiers réels portent 36.x, 37.0.0, 37.1.1, 37.2.0, 37.3.0 et la valeur figée
37.3.0 des builds V37.4.0 et V37.4.1 (`BACKUP_VERSION` n'avait pas suivi). Ce champ n'a jamais été lu par le code. La constante
`BACKUP_VERSION` est supprimée : `version` est désormais lu dans la balise `application-version`, mise à jour à chaque version.

## 2. Formats pris en charge

| Format | Origine | Statut |
|---|---|---|
| `MesHeures Backup` avec `data`, `romiMaster` et `plannings` facultatifs | Outils, Données, Export JSON (`mhV30Export`) ; points internes | prouvé par le code et par les tests existants |
| `MesHeures Backup` avec `data` et `exportedAt` | ancien `expo()` d'`app.js` | prouvé par le code (même structure) |
| DB brute (objet avec `days`, sans `format`) | très anciens exports | prouvé par le code (comportement conservé) |
| `MesHeures V33 Export` avec `data` | « ⬇ Sauvegarde » de l'Assistant (`app-v33-assistant.js`) | **nouveau** : `data` est une copie de DB (ligne 67). Était refusé jusqu'ici. ROMI1 et plannings absents, donc les données actuelles sont conservées |
| `MesHeures Encrypted Backup` | sauvegarde chiffrée | refusé par l'import JSON, avec renvoi vers « Restaurer une sauvegarde chiffrée » |
| tout autre `format` | (Dossier probatoire, planning…) | refusé. Avant, un tel fichier pouvait être accepté s'il contenait `days` à la racine |

## 3. Règles de validation (avant confirmation, avant toute écriture)

1. Le document est un objet JSON (pas un tableau, pas une valeur simple).
2. `format` est reconnu (voir ci-dessus).
3. `formatVersion`, s'il est présent, est un entier entre 1 et 3.
4. `data.days` est un objet, et chaque journée est un objet.
5. `s`, `cmp`, `bul`, `romi`, `per` : un objet s'ils sont présents. `periods`, `bulletins`, `constats`, `events`, `reconciliation` : un tableau s'ils sont présents.
   **Absent ou `null`** : valeur par défaut historique, aucun refus. **Présent avec un type faux** : refus. Avant, le bloc était remplacé en silence par un bloc vide.
6. ROMI1 (`romiValidate`) et plannings (`MHPlanning.store().valider`) : validés comme avant. Ils ne sont lus que dans un fichier `MesHeures Backup`.
7. La nouvelle DB est construite avec les mêmes champs et les mêmes valeurs par défaut qu'avant (`construireDB`).

Le contenu métier (horaires, pauses, repas, paie) n'est pas réinterprété : seules les structures sont contrôlées.

## 4. Déroulement d'un import ou d'une restauration

`mhV30Import` (fichier), `mhV30Restore` (point interne) et `mhV30EncryptedRestore` (chiffré) utilisent le même chemin, `mhV30RestoreCore` :

1. `preparer` : toute la validation ci-dessus. Rien n'est écrit.
2. Confirmation (fenêtre MesHeures, ou `confirm` natif sans le module).
3. `appliquer` :
   1. relevé en mémoire des trois valeurs brutes touchées : `mesheures_v3`, `mh_romi_master_v35`, `mh_planning_v372` ;
   2. copie de sécurité (`before-import`, `before-restore`, `before-encrypted-restore`), **relue après écriture**. Si elle échoue, on arrête : aucune donnée n'est modifiée ;
   3. remplacement de DB, normalisation des repas (`mhNormalizeMealSettings`, `mhMigrateLegacyMealChoices`), `save()` ;
   4. **relecture** de `mesheures_v3` : si elle ne correspond pas à DB (stockage plein, erreur avalée par `save()`), c'est un échec ;
   5. import ROMI1, puis import des plannings ;
   6. `mhRefresh()` une seule fois, à la fin. Avant, l'import l'appelait avant ROMI1 et les plannings.
4. En cas d'échec à l'étape 3.3, 3.4 ou 3.5 : **retour arrière**. DB reprend l'objet d'avant, les trois clés reprennent leur valeur brute d'avant (supprimées si elles étaient absentes), puis chaque clé est relue. Le message indique soit « Données précédentes rétablies », soit les clés non rétablies et la date de la copie de sécurité à restaurer.

## 5. Restauration chiffrée (`app-evidence.js`)

- Défaut corrigé : en V37.4.1, `d` était lu avant `const d=payload.data` dans le même bloc (zone morte temporelle). Toute restauration chiffrée échouait donc, avec le message « mot de passe incorrect ».
- Le message « mot de passe incorrect ou fichier invalide » est réservé à l'étape de déchiffrement. Après le déchiffrement, le message donne la vraie cause.
- La restauration passe par `mhV30RestoreCore`. Elle bénéficie donc de la validation, de la copie de sécurité vérifiée (la copie n'était pas vérifiée avant), de la migration des repas (`mhMigrateLegacyMealChoices` manquait) et du retour arrière.
- L'export chiffré contient désormais `formatVersion` et `plannings`. Les anciens fichiers chiffrés n'ont pas de plannings : les plannings actuels sont alors conservés.
- Champ `version` de l'export chiffré : c'est désormais la version de l'application (balise `application-version`, ou `inconnue` en son absence). Avant, il valait `24.2.0`, figé. C'est une information seulement : la restauration ne la lit pas, et les anciens fichiers restent restaurables.
- Encodage base64 du contenu chiffré : il se fait par tranches de 32 Ko. Avant, `String.fromCharCode(...octets)` recevait tout le contenu d'un coup et dépassait la limite d'arguments de JavaScript sur une grosse base (« Maximum call stack size exceeded »). Le résultat base64 est identique.

## 6. Garanties réelles et limites

Garanti par le code (sous réserve des tests reportés, section 8) :
- un fichier invalide, d'un format inconnu ou plus récent est refusé avant toute confirmation et toute écriture ;
- aucune écriture n'a lieu si la copie de sécurité n'a pas pu être écrite et relue ;
- un échec d'enregistrement de DB, de ROMI1 ou des plannings déclenche le retour arrière, et « Import réussi » n'est plus affiché dans ce cas.

Limites :
- **Pas de transaction** : `localStorage` n'en offre pas. Le retour arrière réécrit des valeurs, et cette réécriture peut elle-même échouer, par exemple si le stockage est plein. La copie de sécurité est alors le recours, et le message le dit.
- La copie de sécurité occupe de la place : sur un stockage presque plein, elle peut échouer. L'opération est alors refusée sans rien modifier.
- `save()` (`app-pwa.js`, non modifié) affiche encore sa propre alerte « Stockage plein » avant le message de MesHeures.
- La rotation garde 5 copies (`prune`, inchangé) : plusieurs exports successifs peuvent évincer la copie `before-import`.
- Aucune empreinte ni signature n'est ajoutée. Un fichier de sauvegarde n'est pas authentifié : n'importe quel fichier bien formé est accepté. Une empreinte jointe au fichier ne prouverait rien contre une modification volontaire. L'intégrité structurelle est contrôlée (section 3) ; l'authenticité ne l'est pas.
- Le module Planning n'exporte rien quand il n'a ni planning ni import, même si des analyses ou `reglages.nomRef` existent : ces éléments ne sont alors pas sauvegardés. Corriger cela demande de modifier le module Planning, ce qui est hors périmètre.
- Aucun écran ne permet de choisir un point de sauvegarde interne à restaurer : `mhV30BackupPanel` n'existe pas, et `mhRestorePreImport` n'est relié à aucun bouton. C'est une décision d'interface à prendre.

## 9. Précautions avant livraison

- **Version et cache (fait, section 10)** : 37.5.0 / 3750, cache `mesheures-shell-v37.5.0`, tous les `?v=` à 37.5.0. Sans ce changement, le service worker aurait continué de servir les anciens `app-backup.js` et `app-evidence.js`.
- Faire un export JSON des données réelles avant d'installer la nouvelle version.
- Un fichier écrit par V37.5.0 (`formatVersion` 3) reste lisible par V37.4.1, qui ignore ce champ. Un futur `formatVersion` 4 sera refusé par V37.5.0, ce qui est voulu.
